 Core setup that changed everything:
    AGENTS.md / CLAUDE.md — Put this in your project root. Tell Claude your project conventions, what tools exist, common pitfalls. It reads this automatically at session start.
    Memory system — Claude forgets between sessions. Create a /memory folder and teach it to checkpoint its work there. I use daily files (YYYY-MM-DD.md) + a MEMORY.md for long-term context.
    MCP servers — These give Claude real capabilities (filesystem, web, databases). Start with the official ones from Anthropic, then add based on your workflow.
For agentic/automation specifically:
The pattern I landed on: Claude Code as the brain, but wrapped in something that handles scheduling, multi-channel messaging, and skill management.
Check out OpenClaw (github.com/openclaw/openclaw) — it's an open-source framework that turns Claude Code into an autonomous agent with:
    Plugin skills for common tasks (email, calendar, GitHub, etc.)
    Persistent memory across sessions
    Scheduling/cron for background tasks
    Multi-channel messaging (Telegram, Discord, etc.)
For skills/plugins, there's also clawdhub.com where people share OpenClaw skills.

# Project Name

Short 1-2 sentence description of what this project actually does. Keep it simple.

## Tech Stack
- Frontend: React 19, TypeScript, Next.js 15, Tailwind CSS v4
- Backend: Node.js, Express, PostgreSQL (Prisma ORM)
- Package Manager: npm (do NOT use yarn or bun)

## Build & Development Commands
- Run local development server: `npm run dev`
- Build the production application: `npm run build`
- Run linting checks: `npm run lint`
- Auto-fix linting errors: `npm run lint -- --fix`

## Testing Commands
- Run all tests: `npm run test`
- Run a specific test file: `npm run test -- src/auth/__tests__/login.test.ts`
- Run tests in watch mode: `npm run test:watch`

## Coding Principles & Rules
- Code Style: Prefer functional components and hooks over class components.
- State Management: Use React Context for global UI state; avoid introducing external libraries.
- Errors: Always handle API errors gracefully and log them using the internal logger utility (`src/utils/logger.ts`).
- Types: Strict TypeScript is enabled. Never use `any`. Define interfaces in `src/types/`.

## Quality & Verification Rules
1. Never assume code works. Always run tests using the testing commands above before marking a task complete.
2. Minimize code impact. Only touch files necessary to complete the prompt. Clean up your own mess.
3. If an introduced change requires a new test file, place it adjacent to the code inside a `__tests__` folder.
4. Do not invent speculative code or draft features that were not explicitly requested.

# C++ Project Memory & Rules

## Build Commands
* Configure CMake: `cmake -B build -DCMAKE_BUILD_TYPE=Debug -DCMAKE_EXPORT_COMPILE_COMMANDS=ON`
* Build Project: `cmake --build build --parallel $(nproc)`
* Clean Build: `rm -rf build`

## Test & Verification Commands
* Run Unit Tests: `cd build && ctest --output-on-failure`
* Format Check: `find src include -iname *.h -o -iname *.cpp | xargs clang-format --dry-run -Werror`
* Apply Formatting: `find src include -iname *.h -o -iname *.cpp | xargs clang-format -i`
* Static Analysis: `clang-tidy -p build src/*.cpp`

## Coding Standards & Invariants
* **Standard**: Target Modern C++20/C++23 practices. Do not use legacy C-style idioms.
* **Memory**: Always rely on RAII. Avoid raw `new`/`delete`. Prefer `std::unique_ptr` and `std::shared_ptr`.
* **Ownership**: Pass cheap-to-copy types by value, heavy objects by `const std::string&` / `const T&`. Use `std::move` for sink parameters.
* **Safety**: Compile with `-Wall -Wextra -Werror`. Ensure code passes with address (`-fsanitize=address`) and undefined behavior (`-fsanitize=undefined`) sanitizers.
* **Null Safety**: Avoid raw pointers for optional values. Prefer `std::optional<T>` or `std::span<T>`.

## File Naming Conventions
* Source files: `src/*.cpp`
* Header files: `include/project_name/*.hpp` or `*.h`
* Test files: `tests/*_test.cpp`
* Case Style: `CamelCase` for class names, `snake_case` for variables and functions, `ALL_CAPS` for macros (avoid macros where `constexpr` or inline functions work).

# CLAUDE.md - Core Project Context & C++ Guidelines

## 🚀 Quick Commands
Always use these exact commands for operations. Do not assume or guess alternatives.

* **Build (Debug)**: `cmake -B build -DCMAKE_BUILD_TYPE=Debug && cmake --build build -j$(nproc)`
* **Build (Release)**: `cmake -B build -DCMAKE_BUILD_TYPE=Release && cmake --build build -j$(nproc)`
* **Run Tests**: `cd build && ctest --output-on-failure`
* **Run Linter**: `clang-tidy src/*.cpp src/*.h -- -Iinclude`
* **Format Code**: `find src include tests -iname *.h -o -iname *.cpp | xargs clang-format -i`
* **Clean Build**: `rm -rf build`

## 📂 Repository Structure
* `include/` - Public header files (`.h` or `.hpp`).
* `src/` - Implementation files (`.cpp`) and private headers.
* `tests/` - Google Test unit tests matching the component structure.
* `cmake/` - Custom CMake modules and external dependency configurations.

## 🛠️ Tech Stack & Requirements
* **Standard**: Modern C++20 (Strictly enforced via CMake configuration).
* **Build System**: CMake (minimum version 3.22).
* **Dependencies**: Managed via CPM.cmake or Git submodules (Check `CMakeLists.txt`).
* **CI/CD**: GitHub Actions workflows handle building, matrix testing, and static analysis.

## 📐 C++ Style & Architectural Guidelines
* **Guidelines**: Strictly adhere to the [C++ Core Guidelines](https://github.io).
* **Memory Management**: Never use raw `new` or `delete`. Prefer RAII and smart pointers (`std::unique_ptr`, `std::shared_ptr`).
* **Ownership**: Pass by value and `std::move` for sink parameters; pass by `const std::string&` or `std::string_view` for read-only strings.
* **Safety & Invariants**: Enforce runtime assertions using `assert()` or contract-style checks for validation.
* **Types**: Prefer explicit type declarations. Use `auto` only when the type is obvious from the initialization or when dealing with complex iterators/lambdas.
* **Error Handling**: Use exceptions for truly exceptional errors; return `std::optional` or `std::expected` (where available) for expected operational failures.

## 🤖 AI Behavior & Verification Rules
* **No Speculative Code**: Only write code that directly solves the given problem. Do not write ahead or add unrequested features.
* **Verification Loop**: After changing any source file, immediately invoke the build command followed by the test suite execution. Fix all warnings.
* **Zero Warnings**: Treat compiler warnings as hard compilation errors (`-Wall -Wextra -Werror`).
* **Sanitizers**: Ensure that code runs cleanly with AddressSanitizer (`ASan`) and UndefinedBehaviorSanitizer (`UBSan`) active during local testing.
* **Self-Improvement**: If you make a mistake due to missing codebase context, immediately ask to update this `CLAUDE.md` file so you do not repeat it.
