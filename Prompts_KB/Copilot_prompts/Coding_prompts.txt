##most common prompts for GitHub Copilot or Copilot Chat to debug, write, and optimize code 

1. Essential Slash Commands

Before crafting custom prompts, use these built-in shortcuts for quick tasks:

    /fix: Generates a suggested fix for selected code.
    /explain: Breaks down complex code or cryptic errors.
    /tests: Generates unit tests based on your function.
    /doc: Adds documentation or comments to your code.

2. High-Leverage Prompt Templates
For Debugging

Instead of pasting an error and hoping for the best, use this structure:

    "Goal: Fix the error in [file/function]. Context: I’m seeing [Error/Behavior]. Expected behavior: [Description]. Here is the code: [Paste Code/Stack Trace]. Please provide: 1) Root cause, 2) Step-by-step fix, 3) Unified diff."

    Pro-tip: Ask it to "Rank the top 3 likely causes" to force it to think through the problem before jumping to a solution.

For Optimization

Avoid the vague "make this better" prompt. Be specific about your performance goals:

    "Optimize this [function] for [performance/memory usage]. Goal: Reduce time complexity from O(n^2) to O(n log n). Constraints: Do not change the function signature. Keep existing logic for [specific edge case]."

    Pro-tip: Ask for "before/after benchmarks" or "Big-O analysis" to verify the improvement.
	
For Writing/Refactoring

Use a "role" and clear constraints to get cleaner code:

    "Act as a senior [Language] developer. Refactor this [function/class] for readability, maintainability, and SOLID principles. Requirements: 1) Do not change external behavior, 2) Add type annotations, 3) Use idiomatic patterns, 4) Explain the changes made."	
	
3. The "CRISP" Framework for Best Results

When you have a complex task, use the CRISP approach to ensure Copilot understands your requirements:

    Context: State the file, library, or specific part of the system involved. Use the # symbol in the chat to reference open files or symbols.
    Requirements: List exactly what the code must do (functional) and what it must avoid (non-functional like performance/security).
    Input/Output: Provide an example of what goes in and what you expect to come out.
    Style/Constraint: Specify naming conventions or libraries (e.g., "Use only standard library," "Match the style of auth.ts").
    Plan: If the task is large, start with: "Propose a plan to implement [feature]. Don't write code yet, just outline the steps."	
	
	
4. Advanced "Pro" Tips

    Iterate, Don't Rewrite: If the first result isn't quite right, don't delete and start over. Send a follow-up: "That's close, but please use an asynchronous approach instead" or "That's too complex; simplify it."

    Ask for Verification: After Copilot writes code, prompt it with: "Write unit tests for this function, including edge cases for [null/empty inputs]."

    Leverage Agents: In VS Code, use the "Agent" mode (via the dropdown in Chat) for autonomous tasks like creating new modules or performing broad refactors across your workspace.

One final piece of advice: If you are ever unsure if the AI is hallucinating a solution, add "If you are unsure, ask me clarifying questions before generating the code" to your prompt. It is the single most effective way to improve accuracy for complex operations tasks.

##CRISP approach copilot prompt example for cpp 

To effectively use the CRISP framework for C++, you need to be explicit about memory management, modern standards (C++17/20), and performance constraints.

Here is an example prompt for a C++ task: writing a thread-safe, fixed-size circular buffer for logging.
The CRISP Prompt Example

    Context: I am working on an embedded logging module in Logger.hpp. I need a high-performance, thread-safe circular buffer for log messages.
    Requirements: Create a templated class CircularBuffer<T, N> with size N. It must support push() and pop() methods. It must be thread-safe using std::mutex or atomic operations.
    Input/Output:
        push(T item): Adds an item. If full, it should overwrite the oldest item.
        pop(T& item): Returns true if successful and populates item, false if the buffer is empty.
    Style/Constraint:
        Use C++17 standards.
        Use std::array for the underlying storage (no std::vector or dynamic allocation).
        Ensure the code is header-only.
        Avoid unnecessary copies; use std::move where appropriate.
    Plan: Outline the class structure first, then implement the push/pop logic, then add the locking mechanism. Please provide the code and a brief explanation of how you handled the race conditions.

Why this works for C++
    Context: Identifying Logger.hpp and the "embedded" nature of the code tells Copilot to prioritize memory efficiency and avoid heavy standard library components like std::iostream if not needed.
    Requirements: Specifying std::mutex or atomics forces the AI to consider the specific threading model you want.
    Input/Output: Providing the function signatures (pop(T& item)) ensures the code fits into your existing architecture without refactoring your entire codebase.
    Style/Constraint:
        "C++17": Prevents the AI from using older C++98 syntax or cutting-edge C++23 features your compiler might not support.
        "No dynamic allocation": This is critical for systems-level/ITOps software to ensure performance and prevent heap fragmentation.
    Plan: Asking for an explanation of race conditions ensures you understand how the safety is guaranteed, which is vital for code review.
	
Quick tips for C++ with Copilot
    Reference Headers: If you have common base classes or specific types you use (e.g., LogMessage struct), mention them: "Use the existing LogMessage struct defined in Types.h."
    Performance: If you are working on high-frequency code, add: "Please prioritize cache-friendly access patterns."
    Safety: Always ask for: "Include static_assert to ensure the template type T is trivially copyable."

CRISP approach copilot prompt example for python 

For Python, the CRISP framework is highly effective for enforcing "Pythonic" code—meaning code that is readable, utilizes standard libraries efficiently, and adheres to PEP 8 standards.

Here is an example prompt for a task: building a script to monitor disk usage and alert if a threshold is exceeded.
The CRISP Prompt Example

Context: I am creating an infrastructure monitoring script in disk_monitor.py. This script will run as a cron job on Linux servers.

Requirements: Create a function check_disk_usage(threshold_percent) that retrieves the root partition usage. If the usage exceeds the threshold, return a dictionary with the status, current usage, and a warning message.

Input/Output:
    Input: threshold_percent (float)
    Output: {"status": "OK" | "CRITICAL", "usage": float, "message": str}

Style/Constraint:
    Use the shutil or psutil library (please choose the most robust one for cross-platform Linux).
    Use Python 3.10+ type hinting.
    Include comprehensive error handling (e.g., if the path doesn't exist).
    Write a docstring using the Google Python Style Guide.
    Do not use hardcoded paths; use os.path or pathlib.

Plan: Outline the imports, implement the usage check with error handling, and finally the logic to compare against the threshold. Please provide the code and explain how you handle potential permissions or path issues.

##CRISP approach copilot prompt example

To illustrate the CRISP framework (Context, Requirements, Input/Output, Style/Constraint, Plan), here is an example of a prompt you might use when you need to write a function that processes IT infrastructure logs in a Node.js environment.
The CRISP Prompt Example

    Context: I am working on an internal IT dashboard in log-processor.js. We need to parse raw server error logs.
    Requirements: Create a function named extractErrorCodes that scans a string for patterns like "ERROR [code]: [message]". It should return an array of unique error codes.
    Input/Output:
        Input: "System check: ERROR 404: Not Found. User error: ERROR 500: Server Down. INFO: System OK."
        Output: ['404', '500']
    Style/Constraint:
        Use modern JavaScript (ES6+).
        Use a Regular Expression for the matching.
        Include JSDoc comments explaining the parameters and return type.
        Do not use any external dependencies.
    Plan: First, define the regex pattern, then implement the extraction logic, then handle the uniqueness filtering. Please provide the code and a brief explanation of how the regex works.

Why this works

    Context (#log-processor.js): By naming the file or referencing it with @file in Copilot Chat, you help the AI understand the surrounding code style and imports.
    Requirements: You define exactly what the function is called and what it does.
    Input/Output: Providing a test case is the best way to prevent the AI from guessing your needs. It gives the AI a "unit test" to aim for.
    Style/Constraint: By specifying "No external dependencies," you prevent the AI from suggesting a library like lodash or ramda if you prefer to keep your bundle size small.
    Plan: By asking for the regex explanation, you ensure the AI creates a solution you can actually maintain and debug yourself.

How to use this in your workflow

When you are in VS Code, simply open the Copilot Chat sidebar and paste this prompt. Copilot will generate the function tailored specifically to your requirements, saving you the time of debugging a generic, "AI-guessed" solution.

CRISP copilot prompt example for python

To get the most professional and maintainable code from GitHub Copilot for Python, you should focus on type safety, performance, and error handling.

Here is a CRISP-formatted prompt for a common Operations IT task: Automating a cleanup script for old log files.
The CRISP Prompt Example
    Context: I am writing a cleanup utility in log_cleanup.py. This script runs daily on our application servers to remove logs older than a specific number of days.
    Requirements: Create a function cleanup_old_logs(directory_path, days_old) that scans the directory, identifies files older than days_old, and deletes them. It must log the names of the deleted files.

    Input/Output:
        Input: directory_path (str), days_old (int).
        Output: Returns an integer representing the count of files successfully deleted.
    Style/Constraint:
        Use pathlib for file system operations.
        Use Python 3.10+ type hinting.
        Wrap the logic in a try-except block to handle PermissionError or FileNotFoundError.
        Ensure the script does not delete directories, only files.
        Add a logging call for every deletion.

    Plan: Please outline the logic: first, validate the directory; second, iterate through files with a timestamp filter; third, perform the deletion with error handling. Please provide the complete function and a main block for testing.

Why this is a "Power User" Prompt
    Safety First: By explicitly stating "Ensure the script does not delete directories," you prevent a common, destructive bug in recursive file-deletion scripts.
    Pathlib Over OS: Requesting pathlib forces Copilot to use the modern, object-oriented way of handling files, which is significantly more readable and less error-prone than the older os.path module.
    Type Safety: Requesting type hints makes the code "self-documenting" and ensures that if another developer (or you, six months later) uses this function, they know exactly what inputs are required.
    Operational Readiness: Requesting logging instead of print statements makes the script production-ready for logging frameworks like ELK or CloudWatch.
Pro-Tips for Python + Copilot
    Contextualize with @: If you have an existing file with logging configurations (e.g., logger.py), open that file in VS Code and include @logger.py in your prompt so Copilot knows how to use your existing logging setup.
    Test-Driven Development: Add: "Include a unit test using the pytest framework that mocks the file system to verify the deletion logic."
    Dry-Run Mode: For operations scripts, add: "Include a dry_run boolean parameter. If True, log which files would be deleted without actually performing the deletion." This is a life-saver for destructive scripts.
