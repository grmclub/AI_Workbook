##List prompts to diagnose errors in large log files quickly

1. Quick Triage & Summarization
When you're handed a massive log file and don't know where to start:

High-Level Summary:
"Analyze the attached log file and provide: 1) A summary of the total error count, 2) The top 3-5 distinct error types by frequency, and 3) The exact timestamps when the highest density of errors occurred."
Anomaly Detection:
"Review this log segment and highlight any abnormal events, unexpected status codes, or unusual patterns that deviate from standard operational logs, even if they aren't explicitly marked as 'ERROR' or 'FATAL'."
Timeline Breakdown:
"Create a chronological timeline of critical errors leading up to the failure event around [INSERT TIMESTAMP], showing the sequence of events step-by-step."

2. Root Cause Analysis (RCA)
When you know an error happened, but need to find out why:
Cascade Analysis:
"Identify the root error in this cascade. Separate the initial triggering failure from the secondary downstream error noise."
Stack Trace Extraction:
"Extract all unique stack traces from this log file. Group similar traces together, name the likely exception type for each, and identify the specific application code line where each failure originates."
Correlation Identification:
"I observed an error [INSERT ERROR NAME/CODE] at [TIMESTAMP]. Search the preceding 5 minutes of logs for related thread IDs, user IDs, or transaction keys to trace what actions triggered it."

3. Performance & Resource Bottlenecks
For slow queries, timeouts, or memory issues:
Latency & Timeouts:
"Find all log entries where processing time exceeded [X] ms or HTTP status codes like 504/408 were returned. List the endpoints or database queries responsible."
Memory & Thread Spikes:
"Scan these logs for warnings related to memory limits (OOM, Garbage Collection pauses), thread pool exhaustion, or connection pool dropouts. Summarize the frequency and context."

4. Extracting Command-Line One-Liners
If the log file is too large to paste directly into an LLM, ask for shell commands to pre-filter it locally:
Generating CLI Commands:
"Give me a set of grep, awk, or sed Linux shell commands to parse a [LOG FORMAT, e.g., JSON / Apache / Nginx / Java Spring] log file to: 1) Count top 10 IP addresses causing 5xx errors, 2) Extract unique stack traces, and 3) Filter entries between [START TIME] and [END TIME]."

Here are ready-to-use LLM prompts optimized for large log diagnostics, plus strategies to deal with volume (since you can’t paste GBs into context).

**Pre-processing strategy for huge files**
- grep -i "error\|exception\|fatal\|panic" file.log | tail -n 200 → feed the result
- awk to extract timestamp + message + stack trace only
- Sample: first 20, middle 20, last 20 errors to catch drift

-------------------------------------------------

### 1. Rapid Triage (First 30 seconds)
```
You are a Site Reliability Engineer. Below are error lines from a large log file.
Task: 
1. Group them by error message/template (ignore timestamps/PIDs).
2. Rank by frequency and severity (Critical / High / Low).
3. For the top 3, state the likely failing component/service.
4. Suggest the single grep/awk command to isolate just those lines.

Log snippet:
[paste 30-100 lines]
```

### 2. Pattern & Noise Filtering
```
This is a noisy production log. Identify:
- True errors vs false positives (e.g., timeout retries that eventually succeed).
- Repeating templates: replace variables with <VAR> and show the pattern.
- Any error that correlates with a specific timestamp range or user-agent/IP.
- One-line summary per unique pattern with a count estimate.

Output as markdown table: Pattern | Likely Cause | Action | Example Line
```

### 3. Root Cause from Stack Traces
```
Analyze these stack traces/exceptions from [service name]. For each:
- Identify the failing function/module.
- Determine if it's a code bug, dependency failure, resource exhaustion, or misconfiguration.
- Highlight the "root" frame (not just the symptom).
- Suggest the fix or config change most likely to resolve it.

Logs:
[paste traces]
```

### 4. Timeline / Correlation (Pre-incident)
```
Build a chronological timeline of events 5 minutes before and after [CRITICAL ERROR / OUTAGE TIME].
Inputs:
- Error logs
- Access logs (status codes)
- System metrics mentions (CPU, memory, disk)

Identify the trigger event: what failed first? Output as bullet timeline with timestamps.
```

### 5. Structured Extraction (JSON/Table for dashboards)
```
Parse these log lines into JSON with keys:
timestamp, level, service, error_code, message_template, user_id/request_id, stack_trace_flag.

Rules:
- Normalize timestamps to ISO.
- Redact PII (replace emails/phones with <REDACTED>).
- If a line is not an error, drop it.
```

### 6. Large-File Sampling Prompt (When you can only paste fragments)
```
I will paste 3 samples from a 10GB log: HEAD errors (first 50 lines), MID errors (around 50% through file), and TAIL errors (last 50 lines).

Compare them:
- Are errors evolving/getting worse over time?
- Are there new error types in TAIL that don't exist in HEAD?
- Estimate if the failure rate is accelerating based on density per time window shown.

Sample HEAD:
...
Sample MID:
...
Sample TAIL:
...
```

### 7. Security / Incident Focus
```
Scan these logs for security indicators:
- Brute force patterns (repeated 401/403 from same IP).
- Injection attempts in query params or headers.
- Unusual access times or geographies.
- Data exfiltration signals (large response sizes + error codes).

Output: Threat Indicator | Evidence (line snippet) | Confidence | Recommended Block/Rule
```

### 8. Generate Query to Find More (Meta-prompt)
```
Based on these error examples, write me:
1. A `grep -E` regex to capture all variations across the full cluster logs.
2. An `awk` one-liner to extract timestamp, service name, and error message only.
3. A `journalctl` or `kubectl logs` command if this is containerized/K8s.
```

---

### Quick Copy-Paste Template
```
ROLE: Senior DevOps Engineer
TASK: Diagnose root cause from logs
CONSTRAINTS: Large file; I only have a sample. Focus on patterns, not single lines.
OUTPUT FORMAT: Table + 3-bullet action plan
LOG SAMPLE:
[PASTE HERE]
```

**Pro tip:** If logs are multi-service, prepend a 1-line header per line like `service=api | ...` so the LLM can correlate across sources without confusion.

####most useful prompts for sre

The most useful AI prompts for Site Reliability Engineers (SREs) target incident response, log analysis, configuration generation, and capacity planning. High-value prompts require precise operational context—such as your tech stack, architecture state, and error logs—to return actionable mitigation steps. 

## Incident Response & Root Cause Analysis
Log Triage: "Analyze these raw error logs [paste logs]. Group them by root cause, rank them by frequency, and tell me which error is likely triggering the cascading failure."

## Postmortem Draft: "Act as a principal SRE. Turn this incident timeline and Slack chat notes [paste text] into a blameless postmortem using the format: Impact, Timeline, Root Cause, and 5 Action Items for prevention."
Alert Translation: "Explain this cryptic Prometheus alert [paste alert/metrics] in plain English. Give me three likely root causes and the exact CLI commands to check each hypothesis." 

## Infrastructure & Configuration
Kubernetes Debugging: "My Kubernetes pod is stuck in [CrashLoopBackOff / OOMKilled] state [paste kubectl describe pod output]. Diagnose the underlying issue and provide the corrected resource limits or YAML fix."
Terraform / IaC Refactor: "Review this Terraform module for [AWS/GCP resource] [paste code]. Identify security vulnerabilities, state drift risks, and write the refactored code following best practices."
CI/CD Pipeline Fix: "This GitHub Actions / Jenkins build failed at step [paste error trace]. Analyze the failure and provide the exact lines to fix the configuration file." 

## Reliability & Toil Reduction
SLO/SLI Design: "Help me define SLIs and SLOs for a high-throughput [describe service, e.g., payment gateway]. Propose a realistic availability SLO, an error budget policy, and two multi-window burn-rate alerts."
Runbook Generator: "Write a step-by-step operational runbook for gracefully restarting our distributed [database/cache cluster] without dropping user traffic."
Bash Script Hardening: "Review and harden this bash automation script [paste script]. Add proper error handling (set -euo pipefail), input validation, and safe retry logic." 

If you'd like, let me know:
Your primary tech stack (e.g., Kubernetes, AWS, Terraform, Prometheus)
The specific operational bottleneck you are facing right now (e.g., debugging an outage, reducing alert noise, writing IaC)
